# Task C genuine original operator and GitHub-event issuance — source candidate (2026-11-05)

## Discovery and finding

Inspected the reviewed root-control PR #40 / PR #39, host-install PR #32, host-deploy PR #26 and repository source/issue history. The gateway's original *issues: opened* dispatcher in `host-deploy/gateway/github_dispatch.py` processes GitHub's event and authorizes SQS submission, but **does not** issue the separate Ed25519 `zog-graphical-task-c-original-github-evidence-v1` envelope, the original operation operator approvals, signed mapping, broker-purpose approval, or revocation approval. Existing producer examples generate **test-only private keys**. No authoritative **live production** issuer key/pin custody, signing executable, webhook capture archive, operator procedure, or issuance receipts could be identified. This is a repository investigation, not proof about undisclosed external infrastructure.

Consequently, **NO claim is made that an issuer, original approval, first S3 genesis, or prior operation was historically approved**. This change proposes a prospective, manually admitted issuance workflow. The issuance CLI is disabled unless a separately protected signer is installed and authentic source records exist.

## Trust topology (five independent roles)

1. **Human operator approval signer**, on a separately secured signing machine, stores one independently enrolled 32-byte Ed25519 seed and a pinned 32-byte raw public key at `/etc/zog/graphical-task-c-issuance/operator.{private,public}`. The code does not generate these keys. A real operator reads the request and purpose before entering `APPROVE sha256:<digest>` on a protected local terminal. One signed identity cannot substitute for an issuer event signature.
2. **Independent GitHub-event evidence issuer**, on a *different* secured machine/principal, stores `event.{private,public}` and a separate `github-webhook.hmac` shared secret. GitHub's original `issues.opened` raw delivery must be received over authenticated HTTPS by a protected capture service, preserving the raw bytes, `X-Hub-Signature-256`, `X-GitHub-Delivery`, capture UTC time and externally verified repository ID. The issuer rechecks the **raw HMAC** before signing. An issue API snapshot, unsigned `GITHUB_EVENT_PATH`, created-by-bot fixture, issue comment, or rerun is **not** a substitute for original delivery. Do not place the webhook secret or event issuer key in GitHub Actions, the gateway or repository source.
3. **Independently protected installer/pin authority** accepts *only* source-verified signed outputs; it separately freezes original Host/installation/STATE IDs, `uuid.UUID(...).hex` request and stage/preflight IDs, existing S3 account/region/bucket/prefix/scope/genesis/**writer role**, original raw event digest and delivery ID, operator/event distinct public-key digests, approved source/unit/wheel RECORD pins, and the broker's public signer pin. It must **never invent or recreate** a missing original checkpoint record, anchored reservation or S3 genesis.
4. **Disabled owner/readonly broker** consumes the independently installed public pins and receipts only. The owner has the separate SSM credential, the broker has only its GetObject-only credential and private signing key, and neither issuance role passes a private key or AWS authority to the gateway.
5. **Gateway** consumes the signed-v2 observation and independently protected public pin only. `NATIVE_TRUST_BROKER_ADMISSION_IMPLEMENTED=False`, `APPROVED_PIN_SHA256=None`, and the owner send hard gate remain until Work's separately authorized native acceptance.

Production key generation and custodial enrollment must occur **outside this package** under approved dual-person ceremony. Separately attest the raw public key fingerprints and install pins by independent secured channel *before* any new event or original approval. Preserve the original pin/history if an external record is missing; treat it as HOLD rather than initialize. Rotating operator/event key requires distinct approved epoch/new scope and never retroactively signs historical events.

## Reproducible prospective issuance

On the already installed and independently attested secure signing hosts, preprovision root-owned `/etc/zog/graphical-task-c-issuance` and `/var/lib/zog/graphical-task-c-issuance/{claims,receipts}/{operator-registry,github-event,operator-purpose,operator-revoke}` directories with exact non-writable owner hierarchy (mode 0700 for private issuer directories). The CLI expects **existing** files; it does not create directories, keys, secrets, pins, original S3 records or trust.

The isolated Python module is `zog.root_control.graphical_task_c_issuance_cli`. Provision an additional protected `claims/github-event-content` directory for an independent raw-delivery SHA fence (same HMAC-authenticated event cannot be reissued under another delivery ID). Run the two signing roles on physically separated trusted signing installations with disjoint credentials and no gateway access. All input manifests are pre-staged root-owned mode 0600. The fixed private key files must be mode 0400, pinned public keys mode 0600, HMAC key mode 0400, all nonsymlink and root-owned. The only outputs are mode 0600, fsynced **create-only** signed receipts and create-only reservation claims. Lost acknowledgement or interrupted signing is **uncertain**: do not delete its claim, retry under a new filename, or reopen the role. Recover by independent read-only inspection and explicit exception authority, not a second signature.

**Step A — corroborate original GitHub event.** Set a private GitHub repository webhook scoped to the exact `issues.opened` event. The new keyless `graphical_task_c_webhook_capture.capture_wsgi` handler may be installed *separately*, behind an independently attested, strictly bounded HTTPS gateway on a capture Host that has **no Ed25519 operator/event key and no SSM or S3 write credentials**. Its externally provisioned HMAC secret, exact GitHub numeric IDs and authorized actor come only from protected installation configuration. It accepts only the original POST `/zog/task-c/original`, refuses invalid signatures and old events, and produces create-only, fsynced mode-0600 receipts with original bytes, HMAC header, delivery ID, request digest and capture time. Work must still configure and attest the actual HTTPS ingress and TLS origin; importing this Python function starts no listener. Use a protected HTTPS receiver preserving the *original request-body bytes*, `X-Hub-Signature-256` and `X-GitHub-Delivery`; its HMAC secret is never in source or gateway. Validate GitHub repository numeric ID and GitHub actor numeric ID against *independently pinned* source, and verify issue author matches sender. The issuer checks that the original issue body has the exact host-deploy fenced request envelope, event action is `opened`, and original creation is within 900 seconds. The raw event SHA-256 and delivery ID are bound to signed evidence. **A fetched current issue body cannot recreate an older opened delivery.** Retain raw delivery and HMAC evidence under independent archive custody; no synthetic event may be backdated.

**Step B — sign operator's two separate original operation grants.** The operator prepares a manifest with exact `stage_request`, independently derived `preflight_request` (same request except `operation_id=preflight_id(request_id,stage_operation_id)`), the exact `stage_original` identity from the real gateway original, two **distinct** pre-existing approval IDs, and an expiry at most 15 minutes from issuance. Review real Host/fingerprint, installation, mounted STATE identity, pinned authority epoch, chosen original `request_id`, stage ordinal, original issue/actor/request digest, monthly/source/base/predecessor and selected operation; verify all using protected original upstream receipts. The operator runs:

```text
sudo /opt/zog/graphical-task-c-issuer/venv/bin/python -I -m zog.root_control.graphical_task_c_issuance_cli operator-registry --manifest /var/lib/zog/graphical-task-c-issuance/input/operator-registry.json
```

The command requires an operator-controlled TTY digest confirmation. It produces both domain-separated v1 original operation approval signatures and operator-signed immutable mapping records, then re-verifies them through `verify_original_operator_approval` and `ProtectedOriginalRegistry`. **No arbitrary send grant** is minted; the owner must still independently claim the two S3 ledger entries and observe preflight success.

**Step C — issuer attest the original GitHub delivery.** After copying the *authenticated, archived* webhook raw body, signature header, approved real operator registry, exact GitHub numerical IDs and pinned original dispatcher/source Git SHA to the distinct event-issuer machine, the issuer runs:

```text
sudo /opt/zog/graphical-task-c-issuer/venv/bin/python -I -m zog.root_control.graphical_task_c_issuance_cli event-from-webhook --manifest /var/lib/zog/graphical-task-c-issuance/input/event-manifest.json --webhook /var/lib/zog/graphical-task-c-issuance/input/original-webhook.json --webhook-signature /var/lib/zog/graphical-task-c-issuance/input/original-webhook.hmac-header --delivery-id <genuine-X-GitHub-Delivery>
```

Preferred form: transfer the original root-protected capture receipt without modification and run `event-from-capture --manifest /var/lib/zog/graphical-task-c-issuance/input/event-manifest.json --capture /var/lib/zog/graphical-task-c-issuance/input/original-capture.json`, which rechecks its raw-event SHA and capture-time age before applying the **same HMAC check**. The low-level `event-from-webhook` form is for independently preserved raw bytes and signature headers; neither mode accepts a mutable GitHub API issue snapshot. The issuer checks SHA-256 HMAC using its separately held webhook secret, exact `opened`, numeric repository/user IDs, author/actor, issue number, immutable gateway `request_id`, and canonical v1 `request_digest` against `original_request_sha256`. It verifies the signed registry under the independent operator public pin. It produces the existing `graphical_task_c_origin` Ed25519 v1 envelope and re-verifies it; the issuance time is trusted machine time (maximum 24h evidence lifetime). The `original_commit_sha` records an independently reviewed, exact 40-character **source checkout revision**, not a SHA asserted to have appeared in an issue-opened payload (it does not). Work must independently establish that revision's GitHub provenance.

**Step D — sign the broker-only purpose.** With the event receipt signed and the *pre-existing* exact checkpoint record, two external anchors, separately installed public pins, actual gateway UID/GID/cgroup/executable digest, owner source revision, broker source, distinct read-only/write/SSM roles and the independently approved public broker signer pin frozen, prepare the separate purpose manifest. Run `operator-purpose --manifest /var/lib/zog/graphical-task-c-issuance/input/operator-purpose.json`. It constructs the existing `graphical_task_c_trust_authority.PURPOSE_SCHEMA` body, binds the event/record/pin SHA-256, Host/installation/STATE/scope, all three different role ARNs and gateway identity, requires human digest confirmation and signs with **operator** key under `PURPOSE_DOMAIN`. Max TTL 15 minutes. Purpose signing never installs an AWS credential or rewrites the S3 tuple.

**Step E — independently inspect and install disabled.** Transfer only signed envelopes, raw event hash/provenance, issuer and operator public-key pins and nonsecret digests across independently authenticated transfer. Re-verify original signed v1 envelopes with pinned keys, exact installed-source/RECORD/unit hashes, genuine external S3 history, original local and independent anchor identities and the mounted STATE before accepting. Preserve the current installed package, interpreter, static/inactive units until Work can prove the actual gateway's UID/cgroup/executable and denial of SendCommand, AssumeRole, IMDS, issuer keys and owner credentials. Record the public fingerprint, source/revision, original issue/delivery/request/operation ID, S3 checkpoint history head and receipt hashes in a separate non-secret acceptance record. A signed receipt is **not** a native GO.

**Step F — expiry, revocation, replay.** No expired v1 operator grant, issuer event or purpose grant may be reused. `operator-revoke --manifest ...` requires a new distinct approval ID, exact selected approved scope, TTL <= 900 seconds and human confirmation; it produces an already supported `REVOCATION_APPROVAL_DOMAIN` signature. Only the protected owner may consume that approval and atomically append an irreversible **S3 revoke** in the original checkpoint, with read-back; a signed revocation receipt alone is not recorded as revoked. Existing and future operations must hold after revocation. Missing/unreadable external history, interrupted receipt publication, duplicate delivery, unknown original identity or old epoch is HOLD, not recovery by recreation.
