## Exact mechanism and uncertainty window

- `root-control/src/zog/root_control/jobs.py` `SystemdJobConnection._execute`: `StartTransientUnit` runs on the privileged system D-Bus connection, `AddRef` is requested, the unit is put in the retained set **before** the RPC, then the implementation waits for a matching `JobRemoved` signal. Its 30-second default deadline covers connection, call and job completion. A local deadline/late signal/lost reply is expressly `operation outcome unknown`; a positive RPC job path alone would not prove successful process execution.
- `root-control/systemd.py` `BusctlSystemdBackend.start_service`: prepares generation-dependent runtime scaffold/persistent paths and issues `StartTransientUnit`; it does **not** return an InvocationID. `root-control/daemon.py` serializes mutating RPCs, then sends a reply. `box-control/runtime/root_control.py` has a 45-second client default, under the caller's operation budget; reply timeout explicitly means request was sent and outcome unresolved.
- `box-control/runtime/systemd.py` `SystemdServiceRuntime.launch`: commits a STARTING reference with `invocation_id=None` before start; observes and durably saves invocation ID **after** a successful service response. A timeout can thus leave a saved runtime without invocation identity even if systemd started it. Generic launch-exception handling attempts kill and cleanup, which can unload the transient unit; it cannot retroactively prove the preparation never executed.
- `box-control/application_storage.py`: the persistent preparation record and step are saved *before* launch. Refresh can accept completion only from exact live unit/boot/invocation/result evidence or an already durably completed matching terminal runtime. Missing unit and missing terminal reference => `uncertain`, not success, not a replay grant. `host-install/certificate_native_observation.py` requires successful prepared step and InvocationID; no inferred terminal success is allowed.

## Recovery decision matrix

| Read-only observation | Safe disposition |
| --- | --- |
| Exact current boot/unit/InvocationID exists, unit still active/activating | **HOLD.** No second start. Preserve PID1 properties and live processes; have controller owner review whether to allow completion or perform explicitly authorized, exact-unit stop after evidence capture. |
| Exact terminal successful unit with result, boot/invocation identity and matching frozen properties | **Candidate for supported recovery only.** Cross-check actual saved durable terminal runtime, step, cgroup drain and storage sync. If the invocation was never durable, **do not hand-edit/publish ready**; implement a reviewed, one-time authenticated evidence adoption/repair with negative tests. |
| Exact terminal failure with corroborated invocation identity and drained cleanup | Preserve evidence, classify failed only through supported reviewed recovery; issuer storage may have partial side effects. Retry is a separate explicit decision after side-effect analysis. |
| Unit absent/unloaded, no exact previously durable success evidence or missing boot/InvocationID | **UNCERTAIN / NO REPLAY.** The service may have run and been unloaded during generic rollback. Absence, successful TCP/D-Bus transport, or empty stdout alone cannot promote ready or justify retry. |
| Mismatched unit/boot/UID/rootfs/command/mounts, active foreign PID, missing ledger/storage identity, storage fault | **BLOCKED.** Protect immutable history and storage, no adoption, no retry; resolve the integrity fault first. |
